# MNT-07 关键缺陷有测试与合并门禁

| 项 | 内容 |
|---|---|
| 类型 | 可维护性 |
| 证据 | EV-08（A/B：源码位置 + Actions 运行截图） |
| 优先级 | P2 |
| 关联 | 线索 10—12、Q6 |
| Issue | #8 |

## 1 现象

上游并非"没有测试"。核对 v0.31.0 源码后确认，官方已配置后端（代码检查 + store、server、internal、
other 四组测试）与前端（代码检查、单元测试、构建）两类检查，且确有对应用例：

- 删除：`store/test/memo_test.go` 的 TestMemoStore 与 TestDeleteMemoStore，检查删除后列表为空；
- 私密笔记权限：`core/access/memo_test.go`、`server/api/v1/test/memo_service_test.go`，检查他人读取被拒、跨账号返回 PermissionDenied；
- 导出导入：`server/api/v1/test/memo_export_test.go`，检查附件名称、路径、大小、内容与导入冲突；
- 草稿缓存：`web/tests/memo-editor-cache.test.ts`，检查草稿保存与重新读取；
- 标签识别：`markdown/markdown_test.go` 的 TestExtractTags。

近期 Actions 列表中有成功记录（#5978，main 分支，绿色对勾），也有失败记录（#5977，PR #6513 触发，红叉）。
查看 #5977 详情：总时长 41 分 12 秒，页面说明为 "This workflow run required approval but was not approved
before it expired."，即审批过期，**没有测试执行失败的证据**。

真正的缺口是三件事：一是界面层的两个完整操作没有测试覆盖——"断网保存后刷新草稿仍在""双击只发一次请求"；
二是并发写入的幂等没有服务端用例；三是没有取得覆盖率，也没有确认这些检查是否为强制合并条件。

## 2 影响

已有的测试集中在后端与解析层，界面层的完整操作链路靠人工回归。这类问题不会在单元测试里暴露，
一旦改动编辑器或保存逻辑，只能靠人手工点，回归成本高且容易漏。

同时，"有工作流"容易被误读成"有质量门禁"。若分支保护未开启，检查失败仍可合并，
测试就只是提示而非约束。

## 3 期望

界面层的两条关键操作有自动化用例；写入幂等有服务端用例；未通过检查的 PR 无法合并；
覆盖率可见且不下降。

## 4 方案

**补用例（3 条）**

- 前端：断网 → 保存 → 恢复网络 → 刷新，断言草稿仍在（对应 EV-01 场景）；
- 前端：双击保存，断言只发出一次 CreateMemo 请求（现有 `disabled={isSaving}` 守卫缺回归测试）；
- 服务端：同 `request_id` 并发提交，断言只落一行（与 MNT-02 配套）。

**开门禁**

- 仓库开启 branch protection，把后端、前端两个工作流设为 required check；
- 覆盖率门槛先设"不下降"，稳定后再提绝对值。

## 5 代价与风险

约 1 人日。风险：门槛设太高会卡住正常提交，先做"不下降"；审批过期的运行不应计为失败，
配置里需要区分"环境原因"与"代码原因"——这一点本次核对已踩到（#5977）。

## 6 验收

- [ ] 三条用例在 CI 中跑通；
- [ ] 未通过检查的 PR 无法合并；
- [ ] 覆盖率不低于改动前；
- [ ] 失败运行的判定能区分"审批过期/环境原因"与"测试失败"。
