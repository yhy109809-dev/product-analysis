# GitHub 仓库使用说明（给不会用的人）

> 仓库已经建好了，这份文件只回答一件事：**里面该放什么，才算是"用 GitHub 合作完成"的作业依据。**
> 全程网页操作，不用装 Git，不用命令行。

---

## 一、先想明白：这个仓库是给谁看的

老师翻仓库，通常只看三样：

1. **有没有过程**——不是最后一天把 Word 传上来，而是能看到谁在什么时候加了什么；
2. **有没有分工**——7 个人是不是都动过，还是一人包办；
3. **有没有闭环**——发现问题 → 提申请 → 改 → 验证，这条链是不是完整。

所以仓库不是网盘，是**证据链**。判断标准很简单：

> 把仓库链接发给一个没参与的人，他能不能只看仓库就明白：你们选了什么软件、怎么装的、发现了什么问题、打算怎么改、改了没有。

## 三、每个位置放什么

### 1. `README.md`（仓库首页）

老师点进来第一眼看到的东西。写四段就够：

```markdown
# Memos 软件工程大作业

研究对象：usememos/memos v0.31.0（本地部署）
课程：软件工程 | 小组：第 X 组

## 成员与分工
| 姓名 | 负责方向 | 本阶段任务 |
|---|---|---|
| 丁 | 部署与运维 | 基线、仓库、统稿 |
| 刘 | 数据存储 | 备份与恢复 |
...

## 目录导航
- [第五阶段任务书](docs/00-任务书.md)
- [改进与建议方案集](docs/05-改进与建议.md)
- [维护申请单](mnt/)
- [证据清单](evidence/)

## 当前进度
- [x] 第四阶段：评测找问题（6 份报告）
- [ ] 第五阶段：改进与建议（进行中）
- [ ] 第六阶段：完成报告
```

### 2. `docs/`（报告正文）

**一章一个文件**，不要把所有内容塞一个巨大的 Word。

- `01-选题与立项.md`：为什么选 Memos、版本、分工、计划
- `02-安装部署.md`：环境、步骤、踩坑、脚本
- `03-现状分析.md`：架构、代码、业务流程
- `04-评测找问题.md`：测试报告、结论清单 C-01～C-10
- `05-改进与建议.md`：8 条提案 + 5 条治理建议
- `06-完成报告.md`：结论、限制、收获
- `台账.md`：一张表，把"结论 → 提案 → 状态"串起来
- `基线卡.md`：环境与版本的唯一口径

**为什么分章**：老师在 GitHub 上能直接看每章的修改历史，谁写的、什么时候改的一目了然，这比一个 docx 有说服力。

### 3. `mnt/`（维护申请单）

一条提案一个文件，六段结构（见方案集）。模板：

```markdown
# MNT-03 超长英文标签撑破页面

- 类型：UI 缺陷
- 证据：EV-02（A/B 级）
- 优先级：P2
- 关联结论：C-03
- Issue：#3

## 1 现象
连续输入 300 个 a 作为标签并保存，笔记详情页 scrollWidth 2955 px，视口仅 1422 px。

## 2 影响
桌面端阅读需横向拖动；移动端整页被撑宽，按钮移出屏幕。

## 3 期望
标签在卡片内省略或换行，页面不出现横向滚动，悬停可见全文。

## 4 方案
- 标签元素：`max-width: 12rem; overflow: hidden; text-overflow: ellipsis;`
- 父容器：`min-width: 0`
- 代价：0.5 人日；风险：短标签被拉宽（用上限而非定宽）

## 5 验收
- [ ] 300/1000 字符英文标签 scrollWidth == clientWidth
- [ ] 中文长标签、普通标签不回归
- [ ] 折叠态可查看全文

## 6 回归
改前/改后截图各一张，4 个用例复跑通过。
```

### 4. `evidence/`（截图）

- 文件名统一 `EV-编号-一句话.png`，例如 `EV-01-并发落库两条记录.png`；
- 正文引用时写"见 EV-01"，不要写"见图3"（图号每改一次就乱，编号不会）；
- 截图三要素：能看到页面或命令、能看到结果、能看到时间或账号；
- **提交前脱敏**：内网 IP、Token、账号换成 `<HOST>` `<TOKEN>` `<ACCOUNT>`。

### 5. `scripts/`（能跑的东西）

`启动Memos.ps1`、`环境自检.ps1` 已经有了，直接传。加上 `backup.ps1` / `restore.ps1` 骨架。

**为什么值得放**：这是"可复现"最硬的证据——别人 clone 下来就能跑。

### 6. `.github/ISSUE_TEMPLATE/mnt.md`

建好之后，任何人点 `New issue` 都会看到"维护申请"模板，六字段自动出现，不会有人漏填。

## 四、网页上的六个操作

### ① 新建文件 / 建目录

仓库首页 → `Add file` → `Create new file` → 文件名里打斜杠就会自动建目录（如 `docs/05-改进与建议.md`）→ 下面 `Commit changes`。

### ② 上传截图

进入 `evidence/` 目录 → `Add file` → `Upload files` → 拖进去 → `Commit changes`。
一次可以拖多张，文件名按 `EV-xx-xxx.png` 改好再传。

### ③ 改别人的文件

点开文件 → 右上铅笔 `Edit` → 改 → `Commit changes`。
**注意**：直接提交会进 `main`。想走流程，就在提交时选 `Create a new branch for this commit and start a pull request`。

### ④ 开 Issue

`Issues` → `New issue` → 选「维护申请」→ 标题 `[MNT-03] 超长英文标签撑破页面` → 填六段 → 右侧选 `Labels` 和 `Milestone` → `Submit new issue`。

### ⑤ 发 PR（Pull Request）

改文件时选"新建分支 + 发起 PR" → 标题 `[MNT-03] 限制标签最大宽度` → 描述里写 `Closes #3` → 右侧 `Reviewers` 选一个人 → 对方点 `Approve` → 你点 `Merge pull request`。

**`Closes #3` 的作用**：合并后 Issue #3 自动关闭，形成"申请 → 修复"的闭环，答辩时特别好讲。

### ⑥ 看谁做了什么

仓库首页 → `Insights` → `Contributors` / `Commits`；或 `Issues` → `Milestones` 看进度。
答辩前截一张 Contributors 图，比口头说"我们分工了"有用得多。

## 七、常见问题

**Q：仓库已经建好了，我该先做什么？**
对照第二节的目录树做一次"体检"：缺哪个目录建哪个，缺 README 先补 README。然后把现有材料（6 份报告、任务书、方案集）按章传上去。

**Q：传错了文件怎么删？**
点开文件 → 右上垃圾桶 `Delete file` → 提交。历史记录会保留，不影响什么。

**Q：两个人同时改一个文件冲突了怎么办？**
先别慌，GitHub 会提示冲突位置，保留两份内容、删掉 `<<<<<<<` 那些标记再提交。更好的办法是**一开始就一人一个文件**，从源头避免。

**Q：图片会不会太大？**
单张控制在 2 MB 内，超过就压缩。仓库超过 1 GB 会变慢，但正常情况下用不到。

**Q：仓库要公开吗？**
按课程要求。要私有就把老师加为 collaborator（Settings → Collaborators），否则老师看不到。

**Q：能不能只用微信群传文件，最后再传仓库？**
不行。老师看的就是"过程痕迹"，最后一天一次性上传，等于告诉老师你们没用 GitHub。
