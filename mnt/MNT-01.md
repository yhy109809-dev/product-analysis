# MNT-01 删除的笔记可恢复（回收站）

| 项 | 内容 |
|---|---|
| 类型 | 功能缺失 |
| 证据 | EV-10（界面走查，C）+ EV-11（源码位置，A） |
| 优先级 | P1 |
| 关联 | C-01、C-09 |
| Issue | #2 |

## 1 现象

界面上删除一条笔记后，笔记从时间线消失，设置页与笔记操作菜单中均无回收站、撤销或恢复入口；
误删后只能通过恢复备份找回。

**删除的实现方式已核实（v0.31.0）**：

- `store/memo.go:392` → `DeleteMemo` 转调 `DeleteMemoWithPolicy`；
- `store/db/sqlite/space_delete.go:94` → `deleteSQLiteMemoSetTx` 依次删分享、删 memo、收集附件；
- `store/db/sqlite/user_delete.go:363` → **`DELETE FROM memo WHERE id IN (...)`**，是物理删除；
- `store/memo.go:407` → 删除后继续清理附件存储快照。

也就是说：删完行就没了，关联的分享与附件也一并清理。`memo` 表本身有 `row_status` 字段
（`store/db/sqlite/memo_delete_policy.go` 读取它，`store/db/sqlite/memo.go:158` 支持按它过滤），
但官方只把它用于 NORMAL / ARCHIVED 两种状态，删除并不走它。

## 2 影响

用户一次误操作即造成内容永久丢失，且附件与分享链接同时消失。对从其他笔记软件迁移来的用户，
习惯性使用"删除"而非"归档"，误删概率更高。现有替代方案 Archive 只能隐藏内容，
且归档会长期占用存储，需要人工清理。

## 3 期望

删除的笔记进入回收站，保留期可配置（默认 30 天）；期间可一键恢复，恢复后正文、标签、
附件与可见性完全一致；超过保留期自动彻底清理。

## 4 方案

既然是物理删除，但状态字段已经存在，**走"复用状态"的路线比新增字段省一半工作量**：

1. `row_status` 增加 `TRASHED` 值，与既有的 NORMAL / ARCHIVED 并列；
2. `DeleteMemo` 不再执行 `DELETE`，改为把 `row_status` 置为 `TRASHED`，记一个 `deleted_ts` 用于计算保留期；
3. 所有列表查询默认过滤 `TRASHED`（`memo.go:158` 已支持按 `row_status` 过滤，主要是把调用点补齐）；
4. 新增 `ListTrashed`、`RestoreMemo`、`PurgeMemo` 三个接口，前端加"回收站"页；
5. **附件清理从删除时推迟到彻底删除时**——现在删除会立即清附件快照，回收站期间必须保留；
6. 后台定时任务清理超过保留期的记录。

只需新加一个时间戳字段用于计算保留期，不需要重建表结构，也不需要迁移历史数据。

## 5 代价与风险

约 2.5—3 人日（接口 1、前端 1、回归 0.5—1）。风险有三处：

- **附件生命周期**：删除时不再清附件，要保证 `PurgeMemo` 时才清，否则会留下孤儿文件或误删回收站内的附件；
- **状态混淆**：Archive 与删除都用 `row_status`，界面上必须分清"归档"与"回收站"，不能合并成一个入口；
- **查询覆盖**：本次只核对了删除路径与状态字段的存在，**没有逐条核对所有查询是否都过滤了 `TRASHED`**，属于部分核对，实施前需补查。

## 6 验收

- [ ] 删除后列表不可见、回收站可见；
- [ ] 恢复后正文 / 标签 / 附件 / 可见性与删除前逐项一致；
- [ ] 回收站期间附件仍可访问，彻底删除后附件才被清理；
- [ ] 超过保留期自动清理，日志可查；
- [ ] 删除后原分享链接立即失效。
