# MNT-02 并发提交不产生重复笔记

| 项 | 内容 |
|---|---|
| 类型 | 可靠性 |
| 证据 | EV-01（A/B 级，待补落库截图） |
| 优先级 | P1 |
| 关联 | C-02 |
| Issue | #3 |


## 1 现象

保持登录状态，绕过界面并发发起两次内容完全相同的 `CreateMemo` 请求：两次均返回
HTTP 200，数据库新增 2 条完全相同的记录。

界面层的连点不会产生重复（保存按钮在请求期间禁用），说明拦截完全在前端。

## 2 影响

脚本、并发请求或网络重放会生成重复笔记，且用户无法从界面上区分哪条是重复的。
对多端同时编辑、弱网重试等场景有实际风险。

## 3 期望

同一次"保存意图"无论重试多少次，只产生一条笔记；接口返回同一条记录，前端表现一致。

## 4 方案

- 客户端为每次保存生成 `request_id`（UUID），随 `CreateMemo` 提交；`proto` 增加 `optional string request_id`；
- 服务端加唯一约束 `(creator_id, request_id)`，或单独建幂等表；
- 冲突时不报错，**返回已存在的那条记录**；
- 前端现有 `disabled={isSaving}` 保留，作为第一道防线。

**关键判断**：不能按"内容去重"——用户确实可能想发两条一样的内容，必须按 `request_id`。

## 5 代价与风险

约 1.5 人日。风险：唯一索引上线前需去重历史数据；旧客户端不传 `request_id` 时退化为原行为。

## 6 验收

- [ ] 同 `request_id` 并发 10 次 → 数据库 1 行，接口 10 次都返回同一条；
- [ ] 不同 `request_id`、内容相同 → 允许落 2 行（不误伤）；
- [ ] 不传 `request_id` 时行为与现状一致。
